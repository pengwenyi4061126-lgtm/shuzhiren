# 商业级数字人直播平台蓝图

## 1. 产品定义

产品不是“生成一个会说话的视频”的工具，而是面向品牌直播团队的数字人直播运营平台。它要使运营人员能在不接触模型细节的前提下，安全地准备商品、编排场次、控制直播、处理异常、复盘成交，并在每一步留下可追溯记录。

产品名称暂定为 `Shuzhiren Studio`。第一期只服务一个组织、少量账号和单路 4090；架构必须为多组织、多直播间、多角色和多 GPU 扩展留出边界。

## 2. 目标与非目标

### 目标

- 让场控在 10 分钟内完成一场已审核直播的准备与预检。
- 让商品价格、库存、赠品、资质和售后回答可追溯到版本化来源。
- 让实时数字人故障时在 10 秒内降级到预制片段或真人接管。
- 将模型、素材、商品、策略、推流和操作统一审计。
- 先支持单路 720p，再横向扩展到多账号和多 GPU。

### 非目标

- 不承诺完全无人直播。
- 不绕过任何平台审核、内容标识或账号规则。
- 不允许 LLM 自行编造商品事实或商业承诺。
- 不在第一期开发复杂 CRM、订单履约或广告投放系统；通过适配器接现有系统。

## 3. 使用角色与权限

| 角色 | 主要权限 | 明确禁止 |
| --- | --- | --- |
| 超级管理员 | 组织、SSO、密钥、角色、数据保留策略 | 日常直接操作直播 |
| 运营主管 | 审批场次、商品版本、策略和发布 | 修改模型或系统密钥 |
| 场控 | 启停直播、插播、切换真人、人工回复、处理告警 | 修改已发布商品事实 |
| 内容编辑 | 管理脚本、预制片段、字幕、人物资产 | 直接推流 |
| 商品审核员 | 审核 SKU、价格、资质、FAQ、风险标签 | 运行媒体服务 |
| 分析人员 | 读取漏斗、回放、审计和导出报表 | 调整生产配置 |
| 开发运维 | 管理部署、模型、GPU、可观测性 | 审批商品内容 |

采用 RBAC 加资源范围限制：组织、直播间、账号、场次、商品目录和数据导出都必须有作用域；所有权限变化需要审计。

## 4. 信息架构与 UI 模块

左侧一级导航固定为八个工作区：

1. **指挥台**：实时预览、推流健康、评论队列、人工接管、告警、插播与切换真人。
2. **场次**：排期、节目单、SKU 顺序、预检、审批、回放和复盘。
3. **内容工坊**：人物、声音、预制片段、脚本、字幕、品牌素材与版本审批。
4. **商品中心**：SKU、价格、库存、活动、资质、售后、FAQ 与数据源同步。
5. **知识与策略**：检索资料、回答白名单、禁说规则、风险分类、转人工规则与提示词版本。
6. **数据中心**：观看、停留、点击、加购、支付、退款、人工接管、风险和稳定性漏斗。
7. **审计中心**：操作日志、模型调用、证据链、回放、导出与数据保留。
8. **系统设置**：组织、成员、角色、渠道、RTMP、模型供应商、GPU、集成、密钥和告警。

### 指挥台的界面规则

- 中心区域永远是直播预览和当前节目单，不能被仪表盘指标挤占。
- 右侧只呈现需要当下处理的内容：评论队列、风险对话、告警和人工回复。
- 底部是时间线：预制片段、实时回答、SKU 切换、人工介入和推流事件可回放。
- 开始、暂停、切真人、结束推流是强制二次确认的命令；插播和回复必须可撤销或可追踪。
- 价格、库存、活动等“事实”显示数据版本与最后同步时间，不能只是普通文案。

### 场次页面的界面规则

- 一场直播是一份可发布的不可变版本；编辑后生成草稿，不直接修改已发布场次。
- “预检”采用明确清单：人物授权、脚本审核、SKU 有效、库存阈值、RTMP、AI 标识、人工值守、GPU 健康。
- 未通过预检时，开始直播按钮不可用，且展示可操作的阻塞原因。

```text

          +------------------------+------------------------+
          |                        |                        |
   Control Plane API         Realtime Gateway        Analytics API
          |                        |                        |
 PostgreSQL + Redis       WebSocket / WebRTC       ClickHouse / BI
          |
   Object Storage (S3/MinIO)
          |
  +-------+----------+----------+--------------------+
  |                  |          |                    |
Content Service  Product Truth  Policy Engine   Audit Service
  |                  |          |                    |
  +------------------+----------+--------------------+
                     |
              Session Director
                     |
        +------------+--------------------+
        |                                 |
  Media Runtime                      AI Runtime
  LiveTalking / FFmpeg              MuseTalk / CosyVoice
  RTMP / preview / recording        ASR / LLM / RAG
```

### 推荐工程框架

| 层 | 推荐 | 选择原因 |
| --- | --- | --- |
| 前端 | Next.js、React、TypeScript、Tailwind、Radix UI、TanStack Query | 企业后台、SSR、权限控制、实时状态与设计系统成熟。 |
| BFF/业务 API | FastAPI、Pydantic、SQLAlchemy、Alembic | 与 AI 和媒体 Python 生态一致，类型与契约清晰。 |
| 实时控制 | WebSocket、Redis Streams | 场控命令和状态推送与 HTTP 事务分离。 |
| 异步任务 | Temporal（生产）或 Dramatiq（P0/P1） | 编码、素材处理、同步、重试和直播恢复必须具备可观察的工作流。 |
| 数据 | PostgreSQL、Redis、S3/MinIO | 事务、缓存/队列、媒体和录屏的标准组合。 |
| 分析 | ClickHouse（规模后引入） | 直播事件和漏斗查询避免压垮事务库。 |
| 媒体 | FFmpeg、OBS 作为备用、WebRTC 预览、RTMP/SRT 输出 | 平台推流与内部低延迟预览解耦。 |
| AI | LiveTalking、MuseTalk、CosyVoice、可替换 LLM Gateway | 将模型封装在工作节点，避免污染业务系统。 |
| 可观测性 | OpenTelemetry、Prometheus、Grafana、Loki、Sentry | 将 GPU、推流、回答质量和业务告警关联到同一场次。 |
| 身份认证 | OIDC、企业 SSO、RBAC | 不在业务系统自造账号与权限。 |

## 6. 服务边界与数据所有权

### Control Plane

负责组织、权限、场次、脚本、商品版本、审核流、策略、直播状态和审计。它是唯一可以写入商业事实和场次状态的系统。

### Media Runtime

负责播放器、媒体切换、字幕、AI 标识、编码、录制、RTMP/SRT、重连和健康探针。它不能直接读取数据库中的未审核商品内容，只接收已签名的场次计划和短期媒体令牌。

### AI Runtime

负责 ASR、RAG、LLM、TTS 和数字人推理。它输出结构化动作建议，不具备直接推流、修改商品或发布场次的权限。

### Product Truth Service

将 ERP/PIM/表格等外部数据同步为版本化事实。每项价格和库存必须包含来源、同步时间、有效区间和审批状态。

## 7. 核心业务流程

### A. 内容与商品上线

```text
导入素材/SKU -> 自动校验 -> 人工审核 -> 生成版本 -> 绑定场次草稿
                                               |
                                          审批发布
                                               |
                                        不可变场次计划
```

### B. 开播流程

```text
创建场次 -> 编排片段/SKU -> 预检 -> 审批 -> 预览 -> 开播
   |             |             |        |        |        |
 草稿        商品事实版本   阻塞项     权限      测试流    审计开始
```

### C. 互动与风控流程

```text
评论/语音 -> 意图分类 -> 规则检查 -> 商品事实检索 -> 结构化回答
                                  |                         |
                             高风险/无证据              TTS/数字人
                                  |                         |
                               人工接管 <-------------------+
```

### D. 异常流程

```text
GPU/模型异常 -> 立即切预制片段 -> 告警场控 -> 自动重试一次
                                                |
                                      恢复失败 -> 切真人/结束场次
```

## 8. 数据模型（第一期）

核心实体：`Tenant`、`Organization`、`User`、`RoleBinding`、`Channel`、`ChannelCapability`、`LiveRoom`、`Persona`、`VoiceProfile`、`Asset`、`AssetLicense`、`Script`、`Product`、`ProductVersion`、`KnowledgeDocument`、`PolicyVersion`、`ModelRelease`、`Show`、`ShowRevision`、`Run`、`PlaylistItem`、`LiveCommand`、`Interaction`、`Handoff`、`StreamEvent`、`Recording`、`Incident`、`Experiment`、`UsageRecord`、`Entitlement`、`AuditEvent`。

不可变记录：`ProductVersion`、`ShowRevision`、`PolicyVersion`、`ModelRelease`、`LiveCommand`、`AuditEvent`、`StreamEvent`。需要修改时创建新版本；直播回放始终可复原当时的商品事实、策略、模型、脚本和场控命令。

## 9. 质量属性与上线门槛

| 维度 | 第一阶段门槛 |
| --- | --- |
| 安全 | 密钥不进前端、不进日志；最小权限；所有高风险命令审计。 |
| 可用性 | 媒体运行时故障可降级；控制面与推流面相互隔离。 |
| 可恢复性 | 进程崩溃后保留场次上下文、录屏和命令日志；重连不重复发送营销内容。 |
| 合规 | 人物/声音/商品证据可追溯；AI 标识与平台规则作为预检项。 |
| 性能 | 预制内容不依赖模型；实时回答有超时和回退，不阻塞推流。 |
| 可测试性 | 商品事实、策略、对话和媒体命令均可用测试替身验证。 |
| 可观测性 | 每个场次具有关联 ID，贯穿 UI、API、工作流、GPU 与推流日志。 |
| 命令正确性 | 强命令具有幂等键、预期状态、审批记录和可回放结果。 |
| 媒体韧性 | 主运行时异常自动进入备用节目；独立检测黑屏、静音、帧率、A/V 同步与输出连接。 |
| 租户隔离 | `tenant_id` 进入身份、数据、对象存储、缓存、事件、日志、指标和导出策略。 |

## 10. 分阶段计划

### 阶段 0：产品与风险基线

产出角色权限矩阵、数据字典、平台规则检查表、素材授权模板、第一批 SKU 测试集和验收场景。完成后才开始写媒体集成。

### 阶段 1：平台地基

完成 Monorepo、身份认证、租户上下文、组织/角色、密钥管理、设计系统、审计骨架、数据库迁移、对象存储、CI、环境配置和可观测性。

### 阶段 2：场次与媒体 MVP

完成场次、节目单、人物资产、预制片段、预检、Media Runtime、备用节目、输出质量探针、测试推流、录屏、命令协议和场控指挥台。

### 阶段 3：商品与安全互动

完成商品事实、审核流、知识库入库隔离、策略、风险转人工、实时评论队列、结构化回答、提示注入测试、模型发布登记和操作审计。

### 阶段 4：试运行与稳定性

完成连续压测、故障注入、RTMP 断连演练、GPU OOM 降级、回放复盘、漏斗指标和灰度发布。

### 阶段 5：规模化

在单路场次稳定后再增加多账号、第二 GPU、渠道适配器、实验分流、计量/额度、ClickHouse 分析、组织级 SSO 和多区域恢复。

## 11. 团队与治理

最小专业团队：产品/运营负责人、全栈或前端工程师、Python/AI/媒体工程师、后端工程师、测试/运维支持。没有专职 QA 时，发布前必须由非开发者执行验收场景。

每周固定三类评审：商品与合规评审、直播复盘、技术可靠性评审。任何模型效果提升都不能绕过商品事实和策略审核。
