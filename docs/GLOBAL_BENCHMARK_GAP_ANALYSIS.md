# 全球专业直播 SaaS 对标与补项

本文件将当前 `Shuzhiren Studio` 蓝图与专业媒体控制系统、SaaS 架构、AI 风险治理和内容溯源的通用要求对照。目标不是复制某个云厂商，而是把适用于数字人带货的能力转化为可执行的产品决定。

## 结论

当前设计在四件关键事上方向正确：商品事实与 LLM 分离、预制内容降级、场控人工接管、版本化审计。它仍缺少的不是更多模型，而是让系统在失败、攻击、多人组织和长期运营下仍能正确工作的能力。

| 领域 | 当前状态 | 必须补足的能力 | 优先级 |
| --- | --- | --- | --- |
| 媒体可靠性 | 有基础降级描述 | 双输入/备用输出、黑屏/静音检测、替补节目、推流质量 SLO | P0 |
| 直播命令 | 有状态机 | 幂等命令、命令审批、事件溯源、断线恢复与重复动作保护 | P0 |
| AI 安全 | 有禁说与人工接管 | 提示注入隔离、工具最小权限、知识库入库隔离、输出校验与红队测试 | P0 |
| 身份与密钥 | 有 RBAC/OIDC | 租户上下文贯穿、短期令牌、密钥库、Webhook 验签、媒体访问签名 | P0 |
| 质量运营 | 有日志与回放 | SLO、告警分级、运行手册、演练、备份恢复和发布回滚 | P0 |
| 模型治理 | 有固定版本概念 | 模型/权重/素材清单、许可证、评测集、批准门和漂移监控 | P1 |
| 商业化 SaaS | 有组织概念 | 租户隔离、套餐/额度、用量计量、账单、数据保留与导出 | P1 |
| 成交科学 | 有漏斗指标 | 对照实验、归因口径、退款后贡献毛利、策略实验与停止规则 | P1 |
| 内容溯源 | 有 AI 标识和审计 | 溯源声明、素材链路、可选 C2PA/Content Credentials、撤回机制 | P2 |
| 多区域规模 | 有扩展方向 | GPU 调度、容量预留、跨区域灾备、多渠道能力矩阵 | P2 |

## P0：必须在真实试运营前完成

### 1. 媒体可靠性不是“进程重启”

专业直播系统会把媒体输入、处理和输出当作独立故障域。数字人直播需要增加以下组件：

- `Primary Runtime`：MuseTalk/媒体主实例。
- `Standby Program`：不依赖 GPU 的低码率预制循环节目，可在主实例故障时持续输出。
- `Output Watcher`：独立于推流进程检查 RTMP 连接、视频帧率、黑屏、静音、A/V 同步、编码延迟和码率。
- `Failover Director`：按规则切到备用节目、备用 RTMP 或真人接管；所有切换必须是幂等命令。
- `Destination Probe`：开播前验证每个渠道的 Stream Key、允许分辨率、音频格式、AI 标识和账号状态。

将“4 小时无人工重启”升级为明确 SLO：直播时段内有效输出可用性、连续黑屏上限、A/V 同步偏差、命令执行 P95、从主实例切到备用节目的恢复时间。开始时只承诺单活加热备用，不在单 4090 阶段伪装成双活高可用。

### 2. 建立直播命令协议

“开始/暂停/切片段/切真人/结束”不能是普通 HTTP 按钮调用。每个命令必须拥有：

```text
command_id, show_run_id, tenant_id, actor_id, issued_at, idempotency_key,
expected_state, requested_action, approval_requirement, result, trace_id
```

规则：

- 强命令必须比较 `expected_state`，避免双击或网络重试造成重复开始/结束。
- 直播运行时只消费签名的命令流；UI 不能直接控制 FFmpeg 或 GPU 进程。
- 采用 outbox/event log，确保数据库状态变化和运行时命令不会出现一边成功、一边丢失。
- 人工接管、价格变更、策略热更新需要明确的审批级别和回滚动作。

### 3. AI 安全边界：把观众文本视为不可信输入

评论、语音转写、商品详情、外部链接和知识库资料都可能包含恶意指令。必须实现：

- 检索资料与系统策略分开存放；资料只能作为引用证据，不能修改工具权限或系统指令。
- LLM 永远不能获得数据库、推流密钥、RTMP、任意 HTTP、Shell 或“发布场次”权限。
- 所有工具调用使用严格 JSON Schema；价格、库存、赠品只从 Product Truth Service 读取。
- 输出先经过政策验证器；不合规、无证据或超时立即进入固定回复/转人工。
- 建立红队测试集：提示注入、违规功效、诱导改价、索取密钥、数据外泄、长文本耗尽和多轮绕过。
- 对每个模型供应商和模型版本记录数据流向、保留策略、许可证和回退路径。

### 4. 身份、租户、密钥与媒体访问

商业产品不能只在页面里有“组织”字段。`tenant_id` 要进入 JWT、数据库行级策略、对象存储路径、Redis 键、事件、日志、指标和录屏导出策略。

- 推流 Key、模型 API Key、ERP token 存入 KMS/Secret Manager，不进入数据库明文、日志或前端。
- 媒体预览、录屏下载和素材上传使用短期签名 URL；链接具备租户和最小权限范围。
- 所有外部 Webhook 校验签名、时间窗和重放攻击；所有写入接口支持幂等键。
- 生产、预发、开发环境隔离；每个环境有独立密钥、对象存储桶、模型凭据和数据集。

### 5. 运营准备度

增加 `Runbook Center`，而不是只存技术文档：

- 告警按 P1/P2/P3 分级并绑定处理人、响应时间和升级路径。
- 针对 GPU OOM、模型无响应、TTS 超时、黑屏、静音、RTMP 拒绝、库存不同步和违规回答分别定义步骤。
- 每月执行恢复演练：从备用节目恢复、从备份还原、撤销已发布策略、撤回存在风险的素材。
- 定义数据备份、恢复点目标 RPO、恢复时间目标 RTO；必须做实际还原测试。
- 发布用 feature flag、灰度、自动回滚和发布后观测，禁止生产环境手工替换模型文件。

## P1：在开始售卖 SaaS 或多账号运营前完成

### 6. 模型、素材与策略的发布治理

新增 `Release Registry`，统一登记：

- 代码 commit、容器镜像 digest、模型/权重 hash、驱动版本、许可证、训练/素材授权范围。
- 人物和声音授权的有效期、地域、用途、渠道、可否商业化和撤销状态。
- 策略包、提示词、知识库、SKU、场次计划之间的依赖关系。
- 评测集结果：事实准确率、拒答正确率、转人工正确率、口型/音画质量、延迟和资源占用。
- 发布批准、回滚版本和变更原因。

### 7. 商业 SaaS 的租户和计量能力

不要在第一版做完整计费系统，但必须从第一天记录可计费事件：GPU 秒数、合成音频秒数、数字人输出分钟数、转码分钟数、存储 GB 月、录屏下载、活跃账号和 API 调用。

建立 `Entitlement Service`：套餐/试用/额度/超额策略/功能开关。这样以后才能区分单一客户私有化、共享 SaaS、按量计费和企业专属 GPU，而不是重写整个系统。

### 8. 实验与经营数据

数据中心必须从“看板”升级为决策系统：

- 预注册对照：同货盘、相近时段、相同投流或明确校正方法。
- 核心结果：退款后贡献毛利，而非播放量或 GMV。
- 归因维度：渠道、场次、SKU、脚本版本、人物、互动策略、价格、活动和流量来源。
- 停止规则：投诉、违规、退款率、错误回答率或推流故障超过阈值时自动暂停实验。
- 数据延迟、来源、修订状态和隐私等级都在报表中可见。

### 9. 渠道适配器与能力矩阵

每个平台实现为独立 `Channel Adapter`：认证、预检、推流、状态回调、评论、商品挂车、回放、限流和错误码不能散落在业务代码中。

为每一个功能维护能力矩阵：是否支持 RTMP/SRT、分辨率、字幕、互动、商品接口、AI 标识、回放、Webhook、测试环境与 API 限额。场次编辑器根据矩阵阻止不支持的节目配置。

## P2：品牌信任与规模化

### 10. 内容溯源与消费者透明度

现在必须有可见 AI 标识、素材授权和内部审计。下一层可选能力是把人物、声音、素材来源、修改动作、场次版本、政策版本与输出录屏绑定为面向外部验证的溯源记录。

国际标准 C2PA 已定义实时媒体与 Enhanced RTMP 的溯源机制，但目标平台是否保留相关数据尚不确定。因此 P2 应采用“双轨”：平台侧继续遵守其 AI 标识规则；系统侧生成不可篡改的场次溯源包和哈希链，并在支持的输出路径试点 C2PA。

### 11. 规模化运行

- GPU Scheduler：按人物/模型/分辨率/并发给工作负载分配专属或共享 GPU；保护高优先级直播免受批处理影响。
- Capacity & FinOps：按场次预测 GPU、出口带宽、存储和 API 成本，允许设置预算熔断。
- Multi-region DR：控制面可恢复，媒体面按渠道和地域配置备用路径；明确定义哪些场次需要双机或双地域。
- Data Lifecycle：素材、聊天、录屏、审计和分析数据分别制定保留、脱敏、归档与删除策略。

## 更新后的发布关卡

| 关卡 | 允许的范围 | 不可跳过的证据 |
| --- | --- | --- |
| G0 实验室 | 本地预览和合成 | 授权素材、单元测试、模型许可证清单 |
| G1 内部试播 | 不对外或测试账号推流 | 预检、录屏、黑屏/静音监测、人工接管、故障恢复演练 |
| G2 小规模真实运营 | 一个组织、有限 SKU、人工值守 | 商品版本、策略测试、风险集、数据备份、事故运行手册 |
| G3 商业客户 | 多直播间/多个客户 | 租户隔离、SSO、计量、SLO、审计导出、渗透/红队测试 |
| G4 规模化 | 多 GPU/多区域/高价值场次 | 容灾、容量计划、成本控制、渠道能力矩阵、变更治理 |

## 不要过早建设的内容

- 多区域双活、C2PA 实时嵌入、复杂计费引擎、ClickHouse 和多 GPU 调度不应阻塞单账号试运营。
- 但数据模型、命令协议、租户上下文、模型发布登记和事件采集必须从第一版建立；这些事以后补的代价最高。

## 对当前项目的具体修改

1. 将 `Output Watcher`、`Failover Director`、`Release Registry`、`Entitlement Service` 和 `Channel Adapter` 加入服务目录。
2. 将场次 `PREPARE` 状态扩展为：`DRAFT -> REVIEW -> APPROVED -> PREFLIGHT -> ARMED -> LIVE -> DEGRADED -> ENDED -> ARCHIVED`。
3. 将所有直播命令改为异步、带幂等键、预期状态和审计 trace 的命令事件。
4. 在数据模型中加入 `Tenant`, `SecretReference`, `ModelRelease`, `AssetLicense`, `ChannelCapability`, `Entitlement`, `UsageRecord`, `Runbook`, `Incident` 和 `Experiment`。
5. 在指挥台新增：输出质量面板、备用节目状态、命令历史、场次风险级别和一键故障演练入口。
